```markdown
# 지원 및 작성 원칙

## 공고별 근거 선택

- Java/Spring·트랜잭션·대규모 요청: 한정상품 예약 프로젝트를 첫 근거로 사용

## 문항 작성 순서

`문제·업무 맥락 → 내가 맡은 범위 → 실패 조건과 판단 → 구현·비교 → 검증 결과 → 지원 직무에서의 활용` 순으로 쓴다. 기술 이름을 나열하기보다 왜 그 선택이 필요했고 무엇으로 확인했는지를 보여준다. 팀 경험은 협업 방식과 본인 기여를 분리하고, 개인 프로젝트는 설계·실험의 깊이를 증명하는 용도로 쓴다.

## 표현 원칙

- “배워서 성장하겠다”보다 “맡은 범위를 끝까지 검증하고 정리한다”를 사용
- 로컬 부하 실험을 상용 처리량이나 실제 사용자 재현으로 과장하지 않음

- ‘서비스 아키텍트·운영 전문가’처럼 현재 경험보다 큰 직함은 피함
```

```markdown
# 자기소개서 작성 방식 및 결과물 검토 가이드

이 문서는 기업·직무별 자기소개서를 새로 작성하거나 수정할 때 적용한다. 목표는 경험을 많이 보여주는 것이 아니라, **문항이 확인하려는 역량에 맞는 주장 하나를 검증 가능한 근거로 설득하는 것**이다. 지원자는 `불확실한 기능의 상태·실패 조건·성공 기준을 먼저 정하고, 실패를 재현한 뒤 대안을 비교해 서비스 흐름에 연결하는 개발자`로 일관되게 설명한다.

## 1. 초안보다 먼저 구조화한다

각 문항은 아래 순서로 한 줄씩 정의한 뒤 작성한다.

`기업·직무가 원하는 사람 → 문항이 확인하려는 것 → 읽은 뒤 남아야 할 판단 → 이를 증명할 경험과 근거`

- 질문의 모든 요구를 분해한다. 문항 DB의 대분류인 `직무·경험·캐릭터·분석·자유`를 먼저 판단하고, 역량/경험·준비도·팀·도전·혁신·가치관 등 세부 의도를 정한다.
- 지원동기는 일반형으로 처리하지 않는다. `목표·역량·준비도·회사 선택 기준·산업 선택·관심 계기` 중 무엇을 묻는지 구분한다.
- 문항마다 핵심 주장과 역할을 하나씩 배정한다. 여러 문항에서 같은 경험을 쓰더라도 문제, 행동, 배운 기준을 반복하지 않는다.
- 경험을 먼저 고정해 문항에 끼워 맞추지 않는다. 질문에 답하기 가장 강한 근거를 선택한다.

## 2. 문항에 맞는 논리 순서로 쓴다

- **경험·역량형:** 문제·업무 맥락 → 맡은 범위 → 판단과 선택 → 구현·협업 → 검증 결과 → 현재의 기준
- **지원동기형:** 관련 경험 또는 회사 선택 기준 → 해당 기업·직무여야 하는 이유 → 입사 후 맡고 싶은 구체적 문제와 기여
- **성장·도전형:** 처음의 관점 또는 한계 → 이를 흔든 문제 → 시도와 검증 → 판단 기준이 어떻게 달라졌는지
- **협업형:** 공동 목표와 의존 관계 → 본인의 역할 → 동료와 합의한 기준 → 후속 작업이 가능한 결과

첫 문단의 소재를 독자가 모른다는 전제로 대상을 즉시 밝힌다. 근거를 알 수 없는 배움부터 선언하지 않으며, 문단끼리 `그래서 왜 지원했는가`, `그 결과 무엇이 달라졌는가`로 이어져야 한다.

## 3. 기술은 판단을 증명하는 만큼만 쓴다

- 기술명보다 `왜 필요했는지, 무엇과 비교했는지, 어떤 실패를 확인했는지`를 보여준다.
- 역할, 조건, 행동, 결과를 구분한다. 팀 성과를 개인 성과처럼 쓰지 않고 본인의 담당 범위와 동료와의 접점을 명확히 한다.
- 수치는 결론을 바꾸거나 신뢰도를 높이는 것만 남긴다. VU·횟수·지표를 모두 나열해 핵심 판단을 가리지 않는다.
- 기업·직무 정보는 공식 자료를 우선해 안전하게 표현한다. 공개 사실, 프로젝트에서 확인한 사실, 측정 결과, 향후 목표를 섞지 않으며 로컬 실험을 운영 환경의 성과로 확대하지 않는다.
- 구현하지 않은 기술명이나 보장 범위를 붙이지 않는다. 저장소·문서·실험 결과로 추적 가능하고 면접에서 재현해 설명할 수 있는 내용만 사용한다.
- 성장은 “성장했다”는 선언보다 `속도 중심 → 실패 후 데이터와 복구 책임까지 검토`처럼 판단 기준의 변화로 보여준다.

## 4. 문장과 표현을 다듬는다

- 설명보다 구체적인 대상을 쓴다. 앞서 소개하지 않은 `두 프로젝트`, 막연한 `담당자·결과·과정` 같은 표현은 피한다.
- 불필요한 영어, 직무보다 큰 직함, 상투적인 금융·기업 연결 문장을 넣지 않는다. 기술 용어는 정확성과 간결성에 도움이 될 때만 쓴다.
- `X가 아니라 Y`, `~에서 그치지 않고`, 세 항목 나열 같은 반복 문형을 줄인다. 수정한 문장도 다른 문항과 다시 겹치지 않는지 확인한다.
- 한계나 미구현 사항을 보고하는 변명 문장을 별도로 붙이지 않는다. 대신 사실의 조건과 범위를 정확히 써서 과장되지 않게 한다.
- “배워서 성장하겠다”보다 입사 후 무엇을 확인·구현·개선할지를 쓴다. 마지막 직무 연결은 경험에서 자연스럽게 도출될 때만 짧게 둔다.

## 5. 최종 결과물 검토 기준

- **문항 충족:** 질문의 모든 요구에 답했고, 한 문장으로 `주장–근거–직무 의미`를 요약할 수 있는가?
- **논리:** 낯선 독자도 맥락과 대상, 본인 역할을 첫 독해에서 이해하는가? 원인–행동–결과 사이에 비약이 없는가?
- **증거:** 기술 선택 이유와 검증 방법이 있으며, 수치·성과·회사 사실의 출처와 범위가 정확한가?
- **분리:** 문항별 역할이 다르고 경험·교훈·입사 후 포부가 중복되지 않는가?
- **문체:** 작업 목록처럼 읽히지 않고 판단과 변화가 중심인가? 추상어, 과장, 불필요한 영어와 반복 문형을 제거했는가?
- **형식:** 공백과 줄바꿈을 포함한 제한 글자 수 이내인가? 오탈자·혼입 문자열이 없는가? 성명·출신학교·출신지역·연령·가족직업·종교·신체조건·성별 유추 표현이 없는가? 전공과 근무 회사·지점명은 허용 범위로 구분했는가?

결과물은 원칙적으로 `문항별 설계 요약 → 완성 초안과 정확한 글자 수 → 중복·사실·블라인드 최종 점검` 순서로 제시한다. 사용자의 피드백은 기존 문장을 부분 보정하는 데 그치지 않고, 구조·역할·근거 선택 기준에 반영한다.
```
