# 자기소개서·이력서 작성용 AI 인수인계

기준일: 2026-09-13. 신입 개인 프로젝트와 기존 인턴·팀 경험을 바탕으로 초안을 작성하고 검토하기 위한 자료다. 완성된 지원서나 채용 기업의 평가 기준을 뜻하지 않는다.

## 읽는 순서

1. [지원자와 경험 지도](01-profile-and-experience-260913.md): 지원 방향, 경험별 본인 역할, 연결 가능한 이야기.
2. [프로젝트 근거 기록](02-project-evidence-260913.md): 과거 버전과 현재 구현, 최신 실험의 확인 범위, 사용할 수 있는 문장.
3. [작성·검토 가이드](03-writing-and-review-guide-260913.md): 문항 설계, 수치 없는 성과, 대안 비교, 최종 검토.
4. [기존 기록 원문](04-original-records-260913.md): 기존 네 문서의 내용을 그대로 보존한 참고 자료. 과거 표현을 최신 사실보다 우선하지 않는다.

파일을 첨부해 사용할 때는 이 다섯 개를 함께 제공한다. 저장소에 접근할 수 없는 AI는 연결된 원본을 직접 확인했다고 말하지 않는다.

## 현재 상태를 먼저 고정한다

- 지원자는 신입이다. 상용 서비스 운영 경험이나 대규모 트래픽 대응 경력을 만들어내지 않는다.
- 과거 재고 전략 비교, 뉴스 생성 팀 프로젝트, AI 인턴 경험은 계속 활용한다. 현재 개인 프로젝트로 모든 문항을 덮지 않는다.
- 현재 Java Target v1에는 재고·결제 상태와 진입 제어 구현, 기능 검증 기록이 있다. 목표인 5만 명 시나리오를 달성한 상태는 아니다.
- 사전 정상 거래를 추가한 warmup은 272건 모두 확정됐다. Worker의 10건/s·120초 실행은 1,201건 모두 확정됐다.
- 등록 전용 실험은 100명/s·60초에서 6,001건을 처리했지만, polling을 포함한 25명/s 실험은 실패했다. 이를 대기열 문제 해결이나 전체 서비스 100 RPS 달성으로 쓰지 않는다.
- Worker·등록 전용 실행의 원본 판정은 `automatedChecksPassed=true`, `status=requires_review`다. 수동 검토 완료·반복 검증 완료로 바꾸지 않는다.
- 현재 작성의 중심은 상태·실패 조건에 대한 판단과 확인한 증거다. 아직 없는 개선율을 얻기 위해 새 구현이나 실험을 필수 조건으로 요구하지 않는다.

## 사실의 우선순위와 표시

현재 실행의 사실은 해당 실행의 config·summary·DB·로그·코드 snapshot을 우선한다. 문서가 더 오래되었으면 원본과 대조한다. 특히 기존 `docs/performance.md`의 “Worker 대기”, `k6/target/waiting-v2/README.md`의 “새 실험 미실행”, 기존 portfolio ledger의 “warmup 실패”는 이 자료 기준으로 일부 오래된 상태다. 이번에는 그 파일들을 수정하지 않았다.

과거 경험은 사용자 제공 기록과 당시 버전 자료로 판단한다. 오래된 실험 수치를 현재 Java 구현에 합치지 않는다. 새로운 사용자 정정은 반영하되 수치와 충돌하면 출처를 확인한다.

초안 검토 메모에는 다음을 구분한다.

| 구분 | 의미 | 가능한 표현 |
|---|---|---|
| 사용자 기록 | 팀·인턴·과거 경험의 제공된 설명 | 담당했다, 적용했다. 세부 근거가 없으면 성과 수치 추가 금지 |
| 구현 | 코드·계약에 존재 | 분리했다, 저장하도록 구현했다 |
| 기능 검증 | 특정 테스트·smoke에서 확인 | 해당 시나리오에서 상태 전이를 확인했다 |
| 부하 관측 | 특정 실행 조건에서 측정 | 로컬 1회 실행에서 …을 관측했다 |
| 해석·가설 | 증거가 지지하지만 원인 확정은 아님 | 가능성을 보고 조사했다, 조사 범위를 좁혔다 |
| 계획 | 아직 실행·확인하지 않음 | 후속 검증 대상으로 남겼다 |

## AI에게 전달할 작업 지시 예시

> 첨부한 자료로 [기업/직무]의 [문항/글자 제한] 초안을 작성해줘. 먼저 문항 의도·핵심 주장·경험·근거 ID를 짧게 정리해줘. 수치 없는 설계 판단도 활용하되 구현, 기능 검증, 부하 관측, 원인 가설을 구분해줘. 인턴과 팀 경험을 삭제하거나 현재 개인 프로젝트의 성과로 합치지 말아줘. 실제로 비교하지 않은 대안을 실험했다고 쓰지 말고, 본인 기여나 기업 정보가 부족하면 필요한 항목만 확인해줘. 마지막에는 글자 수와 사실·중복·공고별 블라인드 검토를 보여줘.

## 이번 갱신의 작업 범위

기존 네 문서, 프로젝트 계약·설계·검증 문서, 9월 13일 여섯 실행의 결과와 주요 집계를 읽어 정리했다. 최신 실행의 모든 raw 표본을 재분석하거나 자동 판정을 재실행한 종합 성능 인증은 아니다. Docker·실제 부하·애플리케이션 테스트는 실행하지 않았고, 코드·자원 설정·기존 문서는 변경하지 않았다. 지원자 본인의 판단 시점과 설명 가능 범위는 최종 제출 전에 확인한다.
