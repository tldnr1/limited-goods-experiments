# 지원자 프로필과 경험 지도

기준일: 2026-09-13. 근거 ID는 [프로젝트 근거 기록](02-project-evidence-260913.md)을 따른다. 기존 설명 전체는 [원문 보존본](04-original-records-260913.md)에 있다.

## 지원 방향과 공통 정체성

Java/Spring 백엔드를 중심으로 지원하되 Python·AI 경험을 함께 활용한다. 대기업은 IT·플랫폼·AI 활용 직무까지 검토하고, 중견·스타트업은 실제 개발 비중이 높은 공고를 우선한다. 이는 지원자의 선택 기준이며 기업별 채용 수요를 조사한 결론은 아니다.

공통 정체성 후보:

> 요청 접수 이후의 상태와 실패 조건까지 살피고, 구현한 동작을 실험과 기록으로 확인하는 백엔드 개발자.

기존의 “실패를 재현한 뒤 대안을 비교해 서비스 흐름에 연결하는 개발자”도 사용할 수 있다. 다만 모든 경험에서 장애 재현과 실측 비교를 수행한 것처럼 반복하지 않는다. 예방 구현은 요구사항과 판단 근거로 설명한다.

## 경험별 보존 내용과 사용 범위

### P1. 한정상품 예약 개인 프로젝트 — 현재 Java/Spring

- Java 21 / Spring Boot 3.5 / PostgreSQL 기반으로 다중 상품 점유, 주문, 비동기 결제, 만료·재확인 흐름을 구현했다.
- PostgreSQL을 재고 원장으로 두고 Redis는 대기·구매 진입 제어에 사용한다. READY 발급은 재고 확보와 다르다.
- 결제 접수의 HTTP 202와 최종 확정을 분리하고, 결과가 불명확한 결제의 재고를 시간만으로 반환하지 않도록 설계했다.
- 기능 검사와 소량 smoke 기록이 있으며, 최근에는 초기 비용과 본 측정을 분리하고 Worker·대기 등록·polling 경로를 나눠 관측했다.
- 현재 강점은 트랜잭션 경계, 멱등성, 실패 상태의 처리 책임, 측정 조건을 설명할 수 있다는 점이다. 고성능 달성·실서비스 운영 경험으로 포장하지 않는다.

활용 문항: 직무 역량, 기술 선택, 문제 분석, 학습 기준의 변화. C1·C2·N1·N2를 우선 검토하고 N3~N6은 미해결 조사 사례로 사용한다.

### P2. 한정상품 예약의 과거 구현·실험

이 경험을 현재 구현으로 대체하거나 삭제하지 않는다. 과거 재고 초과 판매 재현과 원자 UPDATE·비관적 락·Redis Lua 비교는 독립적인 근거다. 현재 구현까지의 변화는 “무엇을 정합성의 범위로 보게 되었는가”라는 연결 후보다. 당시 실제 선택 이유였는지는 본인에게 확인한다.

기존 사용자 기록의 수치도 보존한다: 총 60회 실험, 1,000 VU에서 Redis Lua 평균 p95 340.32ms, 3,000~10,000 VU에서 성공 주문 100건·주문/재고 차이 0건. 다만 이번에는 그 숫자의 원본 행·집계식을 재검산하지 않았다. H0으로 관리하며 제출 전 당시 버전과 집계 범위를 확인한다.

기존 저장소 ledger에는 별도로 초과 판매 재현, Redis 차감 후 DB 실패 주입, 이전 v3.2 Front Gate 비교가 정리되어 있다(H1~H3). 서로 다른 행렬·실행 횟수이므로 “총 60회”에 임의 합산하지 않는다. Python 보존 결과도 현재 Java 수치에 섞지 않는다.

활용 문항: 문제 해결, 대안 비교, 수치가 필요한 기술 성과, 실패에서 바뀐 판단 기준. 제출할 숫자의 원본을 확인하면 현재 warmup 이야기보다 핵심 근거가 될 수 있다.

### T1. 7인 뉴스 생성 팀 프로젝트

사용자 제공 기록:

- LangGraph·FastAPI 기반 비동기 처리 흐름을 담당했다.
- HTTP 202와 작업 ID로 긴 작업을 분리하고 S3와 Spring Boot callback을 연결했다.
- 중복 실행 차단, 실패 상태 정리, 120초 제한, 이미지별 최대 3회 재시도를 적용했다.

120초와 최대 3회는 구현 정책 수치다. 응답 속도 개선율이나 실제 성공률이 아니다. 프로젝트 전체 또는 Spring Boot 영역 전체를 혼자 구현했다고 확대하지 않는다.

활용 문항: 협업, 역할 간 API 계약, 긴 AI 작업의 상태 관리, Python/FastAPI 직무 역량. 협업 문항에 필요한 구체적인 합의·충돌·피드백 일화는 현재 자료에 없으므로 만들어내지 않는다. 본인 코드/PR, 담당 범위, callback의 성공·실패 계약, 실제 테스트 사례를 추가로 받으면 초안을 구체화할 수 있다.

현재 개인 프로젝트와 연결하는 문장 후보:

> 뉴스 생성 서비스에서 작업 접수와 완료를 분리한 경험을 바탕으로, 개인 프로젝트에서도 결제 접수 이후의 확정·재확인 상태를 명시했습니다.

이 문장은 실제 경험 순서와 영향 관계가 맞을 때만 사용한다. 그렇지 않으면 “두 프로젝트에서 접수와 완료의 구분을 다뤘다”는 공통점으로 서술한다.

### I1. AI 부트캠프 및 인턴

- AI 부트캠프 수료 경험을 보존한다.
- 영상 생성 모델·LoRA 실험 인턴으로 모델·데이터·실험 과정을 경험했다.
- 조직 안에서 연구성 작업을 수행한 경험으로 활용한다. 기간, 모델명, 데이터 규모, 평가 지표, 본인 개선 효과는 제공되지 않았다.

원래 기록의 “AI 작업을 실제 서비스 흐름과 연결해 본 조직 경험”은 포지셔닝 의도다. 인턴 중 실제 서비스 통합을 했다는 증거로 사용하지 않는다. 서비스 연결의 구체적인 근거는 T1에서 선택한다. 인턴의 조직 기여를 쓰려면 실험 과제, 비교 기준, 공유·보고 방식, 결과가 후속 판단에 사용된 사례를 확인한다.

### L1. 배포·인프라 학습

Redis, RDBMS, Docker Compose, AWS EC2·GitHub Actions 기반 배포 구조의 학습·설계 경험을 보존한다. 현재 로컬 실험과 별개로, EC2 실배포·운영 기간·CI/CD 자동화 완료 여부는 이 자료만으로 확정하지 않는다. “상용 운영”, “무중단 배포 구축” 등의 성과를 자동 추가하지 않는다.

## 직무별 소재 배치

| 공고의 핵심 | 첫 근거 후보 | 보조 근거 |
|---|---|---|
| Java/Spring·DB·트랜잭션 | P1 상태·트랜잭션, P2 장애 주입·전략 비교 | T1 비동기 API 계약 |
| Python/FastAPI·AI 서비스 | T1 본인 처리 흐름 | I1 모델 실험, P1 상태·실패 설계 |
| Java/Spring와 AI 연동 | T1의 서비스 연결과 P1의 상태 관리 | I1 모델·실험 맥락 |
| 협업·조직 적응 | T1 또는 I1의 실제 상호작용 | 개인 프로젝트는 기술 판단의 보조 사례 |
| 도전·성장·문제 해결 | P2의 실패 주입이나 실제 관점 변화 | N1 초기 실패 분석, N3~N6 원인 분리 |

## 시간이 부족할 때의 우선순위

현재 자료로 상태·실패 처리의 구현 판단과 기능 검증 문장은 작성할 수 있다. 개선율이 없는 이유로 쓰기를 미루지 않는다. 수치가 필요한 한 문항에는 원본을 확인한 과거 실험을 선택하고, 최신 Worker 결과는 해당 조건의 확인 수치로 보조한다. warmup은 측정 신뢰성을 다룬 사례, Waiting은 아직 해결 전인 조사 사례다.

최소 보충 정보는 지원 공고·문항·글자 제한, 팀/인턴의 구체적 본인 행동, 선택 당시의 실제 생각이다. 자기소개서 작성을 위해 새로운 시스템 기능이나 대규모 실험을 먼저 요구하지 않는다.
