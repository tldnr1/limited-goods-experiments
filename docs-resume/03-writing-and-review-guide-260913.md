# 자기소개서·이력서 작성 및 검토 가이드

기준일: 2026-09-13. [경험 지도](01-profile-and-experience-260913.md)와 [근거 기록](02-project-evidence-260913.md)을 함께 사용한다. 특정 기업의 합격 공식이 아니라 이 지원자의 경험을 정확하게 설명하기 위한 기준이다.

## 1. 초안 전에 문항 역할을 정한다

`기업·직무의 요구 → 문항의 확인 의도 → 남길 핵심 주장 → 경험·본인 역할 → 근거 ID`를 한 줄씩 정리한다.

- 문항의 모든 요구를 분해한다. 직무·경험·캐릭터·분석·자유 유형을 구분하고 역량·준비도·팀·도전·혁신·가치관 중 무엇을 묻는지 확인한다.
- 지원동기는 목표·역량·준비도·회사 선택 기준·산업 선택·관심 계기 중 요구에 맞춘다. 회사명만 바꾼 기술 경험문으로 만들지 않는다.
- 문항마다 하나의 핵심 판단을 배정한다. 같은 프로젝트를 재사용해도 행동·교훈·포부를 반복하지 않는다.
- Java/DB 직무에는 개인 프로젝트, AI/Python 직무에는 뉴스 생성 팀 경험을 우선 검토한다. 협업에는 실제 합의와 역할의 접점이 있는 팀·인턴 경험을 고른다.
- 회사·직무 사실은 해당 시점의 공식 공고·자료로 확인한다. 이 자료에는 지원 기업이 지정되어 있지 않다. 대기업 또는 서비스 기업 전체가 숫자만 평가한다고 가정하지 않는다.

## 2. 모든 경험을 장애 해결 이야기로 바꾸지 않는다

| 실제 경험 형태 | 자연스러운 서술 순서 | 피할 비약 |
|---|---|---|
| 관측한 실패를 해결 | 현상·조건 → 원인 근거 → 선택·변경 → 같은 조건의 확인 | 가설을 확정 원인으로 쓰기 |
| 예방 설계·구현 | 요구사항 → 발생 가능한 실패 → 비교 기준 → 구현한 경계 → 테스트·설명 가능한 범위 | 실제 장애가 있었다고 꾸미기 |
| 이론적 대안 비교 | 프로젝트 제약 → 대안의 보장·비용 차이 → 선택 이유 → 미확인 효과 | 논리 비교를 벤치마크로 쓰기 |
| 실측 후 기존 방식 유지 | 비교 목적 → 조건·지표 → 관측 결과 → 변경하지 않은 이유 | 전역 최적·개선 완료라고 쓰기 |
| 조사 진행 중 | 재현한 현상 → 나눈 조건 → 확인·배제한 범위 → 남은 가설 | 원인 제거·해결 성과로 마무리하기 |

경험·역량 문항은 맥락→본인 역할→판단→구현/협업→확인→현재 기준으로 쓴다. 성장·도전은 초기 관점→문제→시도→바뀐 판단 기준, 협업은 공동 목표·의존 관계→본인 역할→실제 합의→후속 작업에 준 결과로 쓴다. 지원동기는 경험·회사 선택 기준→해당 기업/직무와의 구체적 연결→기여할 문제로 잇는다.

## 3. 수치 없는 문장의 효용과 작성 기준

수치가 없어도 기술 선택과 구현 범위가 구체적이면 설계·판단 역량의 근거가 된다. 다만 처리량·지연의 개선을 증명하는 문장과 증명하는 대상이 다르다. 어떤 문장이 채용에서 더 유리한지는 문항·직무·증거의 질에 따라 달라지므로 동일 효용을 보장하지 않는다.

“멱등성을 적용했다”보다 어떤 중복과 실패를 다루는지 쓴다. 테스트가 없다면 “구현했다”까지, 특정 테스트가 있다면 그 조건에서 “확인했다”까지 쓴다. “장애가 발생하지 않았다”는 제한된 관측 사실이며 발생할 수 없다는 보장은 아니다.

현재 사용 가능한 예시(C1/C2):

> 결제 응답이 유실됐을 때 결과를 확인하기 전 재고가 반환되는 상황을 고려했습니다. 결제 시도를 저장하고 동일 시도로 재확인하도록 구현했으며, 결과가 불명확한 동안에는 재고를 보유하도록 상태 전이를 정했습니다.

> 다중 상품 구매에서 일부 상품만 점유되는 것을 막기 위해 주문·점유·재고 변경을 한 DB 트랜잭션으로 묶고, 상품 락 획득 순서를 통일했습니다.

이는 작성 예시다. 실제 설계 당시의 생각이었는지, 관련 코드와 한계를 본인이 설명할 수 있는지 확인한다. 사후에 CS 이론으로 정리한 이유라면 “구현을 검토하며 … 관점에서 선택을 정리했다”로 시점을 맞춘다.

## 4. 대안 비교를 정확하게 쓰는 방법

현재 구조를 설명하는 비교 축 후보:

| 선택·비교 축 | 설명할 수 있는 판단 | 실측 없이 쓰면 안 되는 효과 |
|---|---|---|
| PostgreSQL 원장 vs Redis 차감 후 DB 반영 | 단일 DB 트랜잭션 범위와 저장소 간 실패·보상 책임의 차이 | 현재 RDB가 더 빠르거나 모든 실패에서 우월함 |
| 동기 PG 호출 vs 영속 접수 후 Worker | 접수와 완료의 계약, 외부 호출 동안 DB 트랜잭션을 잡지 않는 경계 | 처리량 N배, 장애 전파 완전 차단 |
| 미확정 결제의 재고 반환 vs 보유·재확인 | 늦게 확인되는 성공과 재판매 충돌을 피하려는 선택, 장기 보유의 비용 | 영구 UNKNOWN 자동 해결·손실 0 |
| 기동 증설/JIT 설정 vs 사전 정상 거래 | 이번에는 자원·JIT를 유지하고 작은 사전 실행 조건을 확인 | 다른 대안을 모두 실험했고 현재 방식이 최적 |

이 표는 검토 가능한 논리 축이다. 실제로 당시 비교·프로토타입·실측을 했다는 사실을 새로 생성하지 않는다. H2처럼 실제 비교가 있는 항목만 실험 결과와 연결한다.

초기 구현을 유지한 경우의 일반 서술 틀:

> [조건]에서 [대안]을 비교했으나 [지표]의 일관된 개선을 확인하지 못했습니다. [추가 복잡성/유지 비용]을 감수할 근거가 부족해 기존 방식을 유지하고, [어떤 조건이면 재검토할지]를 정리했습니다.

현재 프로젝트에서 이 결론의 실험이 완료됐다는 뜻은 아니다. 실제 결과가 생겼을 때만 괄호를 채운다. 수치 차이가 작다는 사실만으로 통계적으로 동일하거나 최적이라고 단정하지 않는다.

## 5. 현재까지 쓸 수 있는 문장과 우선순위

| 목적 | 문장 후보 | 근거·조건 |
|---|---|---|
| 설계 역량 | 결제 시도를 영속화하고 응답 유실을 동일 시도로 재확인하며, 미확정 결제의 재고를 유지하도록 구현했습니다. | C1. 실제 PG 운영 성과 아님 |
| 기능 확인 | 실제 DB 기반 테스트와 소량 HTTP 확인으로 점유·결제 상태 전이와 응답 유실 후 재확인을 검증했습니다. | C2. 당시 기능 범위 |
| 실험 판단 | 사전 정상 거래를 별도 구간으로 실행한 후속 warmup에서 272건 모두 확정되고 Payment 커넥션 획득 timeout이 관측되지 않았습니다. | N1. 로컬 1회, JIT 단독 원인 미확정 |
| 제한된 수치 | 예열 후 로컬 Worker 실험에서 10건/s로 120초간 요청한 실제 1,201건이 모두 확정됐습니다. | N2. 구매 전체 용량이나 개선율 아님 |
| 진행 중 분석 | 대기 등록과 polling을 분리해 등록 전용 부하의 동작을 확인하고, polling 포함 실험의 유입 누락과 응답 오류를 구분했습니다. | N3~N6. 해결 주장 금지 |
| 과거 대안 비교 | Redis 차감 후 DB 저장 실패를 주입해 두 저장소의 상태 불일치를 확인하고, 단일 DB 트랜잭션과 별도 보상의 책임 범위를 비교했습니다. | H2. 제출 전 당시 원본 확인 |

이력서에는 직무와 가장 관련 있는 2~3개 판단을 고르고, 자세한 조건·한계·원본은 프로젝트 설명 또는 면접 자료에 둔다. 핵심 조건을 제거해 의미를 바꾸지는 않는다. 자기소개서는 한 소재를 깊게 설명하고, 최신 warmup·스크립트 작업을 모든 문항의 주인공으로 삼지 않는다.

최신 성능 개선이 미완료여도 C1/C2와 과거 비교가 남는다. 새로운 실험을 하지 않는다면 N3~N6은 조사 사실까지만 쓴다. 테스트 도구 준비를 서비스 처리량 개선으로 바꾸지 않는다.

## 6. 숫자·인과·역할 검토

- 목표 사용자 수, VU, 신규 사용자 도착률, HTTP 요청률, 결제 접수율, 최종 확정률을 구분한다. 설정 200건을 실측 200건으로 복사하지 않는다.
- p95/p99의 endpoint·status·단위와 측정 구간을 확인한다. 성공한 202 지연과 실패율을 함께 검토한다. 202는 결제 성공이 아니다.
- “13→0”이 Hikari timeout인지 HTTP 500인지 최종 실패 주문 수인지 구분한다. 재시도 때문에 각 수치는 같지 않을 수 있다.
- 한 번의 실행에서 오류 0은 그 조건의 관측이다. 최대 용량·모든 장애의 보장으로 확장하지 않는다.
- JIT·CPU quota·클래스 로딩은 가설과 일반 메커니즘을 구분한다. 현재 증거로 특정 JIT 임계치나 완전 예열을 주장하지 않는다.
- CPU 상한 근처 사용량만으로 throttling, 메모리 한계, 유일 원인을 확정하지 않는다.
- 비교의 자원·코드·PG 지연·예열·VU·사용자 행동이 달라졌다면 그 차이를 밝힌다. 진단용 다른 시나리오를 최적화 전후로 사용하지 않는다.
- 팀 성과와 본인 기여, 인턴의 모델 실험과 팀의 서비스 통합을 분리한다. 협업 갈등·합의·피드백·회사 기여를 지어내지 않는다.
- AI 도움을 받은 작업은 본인이 검토·선택·실행·해석한 범위에 맞춘다. 사용자가 실행한 부하를 AI가 실행했다고 쓰지 않으며, 지원자가 설명할 수 없는 코드까지 독자적 판단으로 포장하지 않는다.

## 7. 문체와 최종 산출물

첫 문장에서 대상과 문제를 소개한다. 기술명 나열보다 선택의 이유와 달라진 동작을 연결한다. 경험 맥락 없이 “성장했다”부터 선언하지 않는다.

- 소개하지 않은 “두 프로젝트”, 막연한 “담당자·결과·과정” 대신 구체적인 대상을 쓴다.
- 불필요한 영어, “서비스 아키텍트·운영 전문가” 같은 큰 직함, 근거 없는 금융·기업 연결은 피한다.
- “X가 아니라 Y”, “~에 그치지 않고”, 세 항목 나열을 반복하지 않는다.
- 내부 검토 문서에는 한계를 분명히 남긴다. 제출 초안에는 변명 문단을 늘어놓기보다 “로컬 1회”, “Mock PG”, “해당 조건”처럼 필요한 범위를 문장 안에 적는다.
- “배워서 성장하겠다”보다 경험에서 이어지는 구체적인 확인·구현·개선 대상을 쓴다. 문항에서 요구하지 않으면 억지 포부를 덧붙이지 않는다.

최종 체크:

1. 문항의 모든 요구에 답하고, 주장–근거–직무 의미를 한 문장으로 요약할 수 있는가?
2. 처음 읽는 사람도 대상·역할·판단 이유를 이해하는가? 관측에서 원인·개선으로 가는 비약은 없는가?
3. 숫자와 사실의 출처·버전·측정 조건이 맞는가? 미실행 목표나 가설을 성과로 쓰지 않았는가?
4. 문항별 소재와 결론이 중복되지 않는가? 팀·인턴·개인의 역할 구분이 유지되는가?
5. 수식어보다 행동·판단이 중심인가? 오탈자·혼입 문자열·불필요한 기술명이 없는가?
6. 실제 공고의 글자 계산 방식과 제한에 맞는가? 공백·줄바꿈 포함 여부를 확인하고 계산한다. 도구로 세지 않았다면 정확한 글자 수라고 말하지 않는다.
7. 블라인드 규정은 해당 공고를 따른다. 성명·학교·출신지역·연령·가족직업·종교·신체조건·성별 유추 표현을 요구 범위에 맞춰 점검하고, 전공·근무 회사·지점명 허용 여부도 확인한다. 모든 일반 이력서에 일괄 삭제 규칙을 적용하지 않는다.

AI 출력 순서: **문항별 설계 요약 → 완성 초안과 계산한 글자 수 → 근거 ID·확인 필요 사실 → 중복·문체·공고별 블라인드 점검**. 제출용 초안 안에는 내부 근거 ID나 미확인 괄호를 남기지 않는다. 사용자의 피드백은 문장 수정뿐 아니라 문항 역할·근거 선택에도 반영한다.
